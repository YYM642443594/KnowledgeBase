# 嵌入式 C 工程典型问题处理模式

> 来自 STM32F103C8T6 工程规范整改实战提炼的「问题 → 处理模式」清单，适用于 Keil + ARMCC 的裸机分层工程。工程背景见 [工程架构说明](../STM32/STM32_F10x/Doc/工程架构说明.md)。

## 一、分层治理类

### 1. APP 直调 HAL（跨层调用违规）

- **问题**：APP 层为图省事直接 include HAL 头并调用 `HalXxx()`，破坏 APP→DRV→HAL 单向链。
- **处理模式：薄转发层**。在 DRV 层新建一个只做参数透传的封装函数（通常 3~5 行），APP 调 DRV，DRV 调 HAL：
  ```c
  /* drv_usb.c —— 薄转发，不含业务逻辑 */
  void DrvUsbSend(const unsigned char *Buf, unsigned int Len)
  {
      HalUsbSend(Buf, Len);
  }
  ```
- **要点**：转发层必须"零逻辑"，否则变成又一层业务；重构后全量 Rebuild 对比 Code 尺寸，净变化应为 0 或极小（纯透传会被编译器优化掉）。

### 2. 下层事件如何通知上层（反向调用违规）

- **问题**：串口收到字节、器件产生中断，数据在下层产生但消费者在上层；DRV 直接调 APP 函数即反向依赖。
- **处理模式：回调注册**。上层初始化时向下层注册函数指针，**注册动作本身是合法的向下调用**；下层只保存指针、在事件点调用：
  ```c
  /* APP 层（初始化时） */
  DrvUartSetRxCallback(UART_CH_AT, AppParseOnByte);
  /* DRV 层（中断上下文） */
  if (p->RxCallback) p->RxCallback(byte);
  ```
- **要点**：回调指针必须判空；回调里不做重活（中断上下文），只搬运/置标志，业务在主循环消费。

### 3. BSP 层悄悄膨胀成业务层

- **问题**：板级支持层逐渐塞入器件初始化、甚至器件驱动逻辑，退化为"第四层驱动层"。
- **处理模式：职责上移**。BSP 只留两样东西——机型配置表（引脚/串口绑定的宏）+ 板级初始化与毫秒节拍；器件初始化上移到 APP 主初始化流程按需调用。

### 4. 厂商库文件被业务引用/修改后失去豁免资格

- **问题**：厂商库源码（如 ST 的 usb_pwr.c）需要新增依赖，或业务代码散落引用厂商库内部函数，分层检查时无法归类。
- **处理模式：厂商库区隔离 + 路径迁移**。所有厂商库统一放独立目录（如 `00.STM32/`）并在构建配置中同步路径；厂商库目录整体豁免分层/命名检查，业务代码永远不进入。
- **厂商契约豁免**：libc 钩子（`_sys_exit`/`fputc`）和厂商库按**函数名**调用的函数（ST USB 库的 `USBCableConfig`/`EnterLowPowerMode`）无法改名，登记豁免清单并在注释注明原因，不算违规。

## 二、资源冲突类

### 5. 引脚/中断向量共用冲突（USB 与 CAN）

- **问题**：F103 的 USB_DP/DM 固定 PA11/PA12，与 CAN 收发脚相同；USB_LP 与 CAN1_RX0 共用一个中断向量——两者物理上不可能共存。
- **处理模式：编译期互斥守卫**。配置头中用 `#error` 把"同时使能"变成编译失败，而不是留到运行期莫名失效：
  ```c
  #if APP_MOD_USBCDC && APP_MOD_CAN
  #error "USBCDC/CAN mutually exclusive (PA11/PA12 shared, vector conflict)"
  #endif
  ```
- **要点**：互斥必须连**向量函数**一起互斥——两个候选 ISR 同名定义会直接链接报错，故向量也用 `#if` 包裹，置 0 的那个连同整条驱动链被链接器剔除（实测关 CAN 组省约 2.5KB）。

### 6. 配置间的依赖关系只写在注释里

- **问题**：使能 A 模块必须同时使能 B（如小车依赖电机、LCD1602 依赖 IO 扩展），忘记后到运行期才暴露奇怪故障。
- **处理模式：依赖显式化为 `#error`**。硬依赖编译期强制；弱依赖（可选功能依赖）运行期拒绝该功能并提示，其余功能不受影响。

## 三、编译期配置与警告类

### 7. 功能裁剪的通用机制

- **问题**：Flash 紧张时需要按配置裁功能，从工程里手工增删文件既繁琐又容易改丢。
- **处理模式：宏开关 + `#if` 包裹调用点 + 链接器剔除**。ARMCC 链接器默认 `--remove`，开关置 0 后调用点消失，整组代码（驱动+厂商库函数）自动不进镜像，改回 1 重编译即恢复。
- **配套守卫**：互斥组用 `#error`（见模式 5），硬依赖用 `#error`（见模式 6）。

### 8. 条件编译产生的死代码警告（statement unreachable）

- **问题**：模块被裁剪后，函数尾部残留的无守卫代码成为"永不可达"路径，编译告警。
- **处理模式：守卫随代码走**。给受裁剪影响的语句补上与模块一致的 `#if APP_MOD_xxx ... #endif` 包裹，而非删代码或压制警告（`#pragma diag_suppress` 会掩盖真问题）。

### 9. 增量编译掩盖警告（改了却"看起来没生效"）

- **问题**：修复某文件的警告后重编译，告警依旧——Keil 增量构建命中了旧 obj，修复根本没参与编译。
- **处理模式：验证必须全量 Rebuild**。任何"警告是否消除"的结论都以全量重建输出为准；对单文件可疑时 `touch` 该文件强制重编，看该文件单独的 `0 Error(s), 0 Warning(s)`。结构重构类改动（如薄转发层）还要对比重建后的 Code/RO/RW/ZI 四项尺寸，确认行为零漂移。

## 四、工程验证方法类

### 10. AI/自动化审查报告的数字不可直接采信

- **问题**：AI 合规审查报告给出"1013 处注释缺失、190 个超长函数"这类宽口径数字，逐项整改工作量被高估数倍。
- **处理模式：脚本实查复核**。用精确脚本复核后再动手：
  - 正则定位函数定义行（`^[A-Za-z_][\w \t\*]*\([^;]*\)\s*$` 且下一行是 `{`）；
  - 向上回溯 `/**` 注释块判断 Doxygen 标签缺失；
  - 花括号计数得函数体行数判超长；
  - 只扫自研目录，排除厂商库豁免区。
- **实测**：AI 报告的 1013 处实查为 28 处，190 个超长函数实查 16 个。审查结论是线索，不是证据。

### 11. 批量改码的编码陷阱（GBK/UTF-8）

- **问题**：工具批量修改含中文注释的源码，部分文件出现 `?` 乱码、代码被破坏。
- **处理模式**：先查 git blob 本源编码（`git cat-file` + `decode('utf-8', strict)`），转换用 Latin-1 作 1:1 字节桥并断言无损往返，全程禁 `errors='replace'`。详见 [嵌入式C工程源码编码陷阱-GBK与UTF8](../03-问题排查/嵌入式C工程源码编码陷阱-GBK与UTF8.md)。

## 一页速查

| 问题 | 一句话处理 |
|------|-----------|
| APP 直调 HAL | DRV 薄转发层，零逻辑透传 |
| 下层通知上层 | 回调注册（注册即合法向下调用） |
| BSP 膨胀 | 只留配置表+板级初始化，器件初始化上移 APP |
| 厂商库引用 | 独立目录隔离+构建路径同步，按名契约函数登记豁免 |
| 引脚/向量冲突 | `#error` 编译期互斥，向量一并 `#if` |
| 配置依赖 | 硬依赖 `#error`，软依赖运行期拒绝 |
| 裁剪功能 | 宏开关+链接器 `--remove` 自动剔除 |
| unreachable 警告 | 守卫随代码走，不压警告 |
| 改了没生效 | 全量 Rebuild + 四项尺寸对比 |
| AI 审查数字 | 脚本实查复核后再动手 |
| 中文乱码 | blob 判源 + Latin-1 无损转换 |
