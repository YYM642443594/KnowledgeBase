# 0x091 时间戳抖动修复报告（2026-10-15）

## 一、测试现象

1000Hz CAN 推送时，0x091（时间戳报文，小端 uint64，单位 us）相邻包时间戳差值
（包2-包1）在 **0.8~1.2ms** 之间波动（步进 0.1ms），长期均值恰为 1ms。理论上应为 1ms。

## 二、根因分析

时间戳产生链路（修复前）：

```text
SysTick_Handler (1ms硬件节拍, gd32f30x_it.c)
  └─ BspSysTickMs()                 ← 仅 RunFlag=1、RunSysTicks++
主循环 1kHz 分支 (bsp_function.c, RunSysTicks % RUN_1000Hz == 0)
  ├─ SensorSystem_ReadData() / BspSensorDataProcess()
  ├─ BspSysRunTimeSet(DWT差值)      ← ★ G_SysRunTime 在此累加
  └─ check_and_send_message() / BspUserDataPushControlCenter()
       └─ 0x091 打包读取 BspSysRunTimeGet()   (bsp_data_interaction.c)
```

**根因**：`G_SysRunTime` 的递增时刻 = 主循环执行到 1kHz 分支的时刻，而非硬件节拍时刻。
主循环执行相位受单圈耗时波动（指令解析、推送、CAN 入队、Flash 处理）影响，
绕 SysTick 边界漂移达 ±200us。DWT 差值累加如实记录了"相邻两圈的真实执行间隔"：
某圈巡回晚 → 差值 >1ms，下一圈补偿 → <1ms（0.8+1.2=2.0ms 的配对特征）。
DWT 方案无累积误差，故均值精确 1ms——与测试现象完全吻合。
**不是 CAN 发送问题，是时间戳源的锁存位置问题。**

## 三、方案对比与选型

| 方案 | 分辨率 | 相邻差值 | 结论 |
|------|--------|----------|------|
| 原实现：主循环 DWT 累加 | 1us | 0.8~1.2ms 波动 | 抖动源为主循环巡回延迟 ±200us |
| SysTick ISR 内 `+= 1000` | 1ms | 严格 1000us | 分辨率退化，无法满足 us 级对齐需求 |
| **选定：SysTick ISR 内时基差值累加（时基源由主工程注入）** | **1us** | **≈1ms ± 中断响应延迟（通常 <±50us）** | 抖动缩小一个数量级，分辨率保留 |

选型依据：读数点移入 SysTick 中断后，抖动源从"主循环巡回延迟（几百 us）"
收敛为"中断响应延迟（几 us～几十 us，仅被 CAN TX 等高优先级中断抢占时出现）"；
DWT 换算同源（核心时钟），PPS 频偏校准（G_SlopeA/G_SkewingB）语义不变。

## 四、修改清单

| 文件 | 修改 |
|------|------|
| `bsp/00.Code/inc/bsp_run_ctrl.h` | 新增 `BspUsTimeSource_F` 时基源函数指针类型（**返回距上次调用的微秒增量**）与注册接口 `BspSysUsTimeSourceRegister()` |
| `bsp/00.Code/src/bsp_run_ctrl.c` | **移除 `#include "dwt.h"`**（bsp 子仓库为共用代码，不得直接依赖 MCU 底层接口）；`BspSysTickMs()` 内直接 `G_SysRunTime += G_UsTimeSource()`（增量累加，无差值基准变量，彻底平台无关）；未注册时不累加 |
| `system/main/main.c`（主工程） | 新增 `SysUsTimeSourceGet()`：内部 `static LastCycles` 基准，`dwt_us_from_cycles32(NowCycles - LastCycles)` 做 32 位差分（无符号减法天然处理 CYCCNT 回绕）后返回增量 us；`dwt_timer_init()` 后先调用一次预热基准，再 `BspSysUsTimeSourceRegister(SysUsTimeSourceGet)` 注入 |
| `bsp/00.Code/src/bsp_function.c` | 删除 1kHz 分支 DWT 累加（`CycleNow`/`LastCycle1ms`/`BspSysRunTimeSet` 共 7 行）及已无用的静态变量 `LastCycle1ms`；200Hz/100Hz 分支的 `last_clock_us`（算法 dt 测量）不受影响 |

依赖注入架构（bsp 共用代码与 MCU 底层解耦，增量契约）：

```text
主工程 main.c（平台相关）                  bsp 子仓库（共用,平台无关）
┌──────────────────────────────┐         ┌──────────────────────────────┐
│ dwt_timer_init()              │         │ BspSysTickMs() (SysTick 1ms) │
│ SysUsTimeSourceGet():         │─注册注入─▶│  G_SysRunTime += G_UsTimeSource();│
│  差分=dwt_cycles32()-LastCycles│        │  (纯累加,增量契约)            │
│  return dwt_us_from_cycles32( │         └──────────────────────────────┘
│    差分)  ←回绕/换算都在此     │
└──────────────────────────────┘
```

自愈设计：时基源注册晚于 SysTick 使能时，未注册期间不累加；主工程在注册前预热一次
基准，注册后首拍增量即为正常 1ms 量级。

## 六、时间戳修改规范（后续约束）

1. `G_SysRunTime` 的累加**只允许**发生在 `BspSysTickMs()`（SysTick 1ms 中断）内
2. 禁止在主循环任何位置调用 `BspSysRunTimeSet()` 累加时间（该 API 保留但不应使用）
3. 0x091 等时间戳消费方只读 `BspSysRunTimeGet()`，不做二次补偿
4. 复位时间必须走 `BspSysRunTimeReset()`（已封装基准清理），不得直接写 `G_SysRunTime = 0`
5. bsp 子仓库共用文件**禁止**直接包含 `dwt.h` 等 MCU 底层头文件或调用底层接口；
   底层能力一律由主工程经函数 API 注入（如 `BspSysUsTimeSourceRegister()` 注册时基源）

## 七、二次问题：注入源回绕周期不匹配（补充，修复待上板复测）

**现象**：上板偶发 0x091 时间戳跳变到 **4259176.902 ms**（约 71 分钟的虚假运行时间）。

**根因**：第一版注入契约让主工程返回 `dwt_us_from_cycles32(dwt_cycles32())`
（把绝对 CYCCNT 换算成"绝对微秒"），但该换算把 2³² 周期映射成 0~35791393 us，
**源的回绕周期变成 35.79s（2³²/120MHz）而非 2³² us（71.6min）**；bsp 侧却按
模 2³² 做差值累加。每当 SysTick 读数跨越 35.79s 回绕点，该次差值被算成：

```text
2³² − 35791394 + 1000 = 4259176902 us = 4259176.902 ms  ← 与实测分毫不差
```

即每次回绕点跨越向 G_SysRunTime 猛加约 71 分钟。"偶尔出现"= 每 35.79s 的
回绕点跨越一次才触发一次。

**教训**：`dwt_us_from_cycles32()` 的设计语义是"差分周期数→微秒"（输入小值），
不能把它的输出当"模 2³² 的绝对微秒"用——换算破坏了回绕周期的一致性
（周期数模 2³² ≠ 微秒数模 2³²）。

**修复**：注入契约改为**增量语义**——主工程 `SysUsTimeSourceGet()` 内部持有
`static LastCycles` 周期基准，返回 `dwt_us_from_cycles32(NowCycles - LastCycles)`
（32 位无符号差分天然处理 CYCCNT 回绕，仅 SysTick 1ms 调用一次、永不漏圈）；
bsp 侧退化为纯累加 `G_SysRunTime += G_UsTimeSource()`，差值/回绕逻辑全部收进
主工程，彻底平台无关。注册前主工程先调用一次预热基准，避免首拍累加上电全量。

**约束补充**：
- 注入源若为增量契约，**只允许**注入方（SysTick ISR）调用，禁止其它位置调用（会偷走增量）
- 注入源若为绝对值契约，必须保证其回绕周期恰为 2³² us，否则差值方不能用模 2³² 处理回绕；
  优先选用增量契约，把平台回绕细节封死在主工程实现内
