# 嵌入式项目架构规范（跨仓库形态 · 通用模板）

## 0. 使用说明

> 本文档为跨工程通用模板，可直接复制到任意 MCU 工程根目录使用，**无需任何修改**。
> 正文统一使用占位符引用工程参数，使用时按当前工程实际结构对应取值。

### 0.1 仓库形态

`<仓库形态>` 二选一，两种形态共用本文档全部规范，仅代码物理位置与版本管理方式不同：

| 形态 | 结构 | `<子仓库>` 的含义 |
|------|------|------------------|
| 形态A：主仓库 + 子仓库 | HAL 在主仓库，DRV/BSP/APP 在独立 Git 仓库 | Git Submodule（第 10 章适用） |
| 形态B：单仓库 | HAL 与 DRV/BSP/APP 在同一仓库 | 主仓库内普通模块目录（第 10 章不适用） |

形态B 下，正文中的 `<子仓库>`（含"子仓库"一词及 `<子仓库Readme>`）统一读作该模块目录及其 Readme，其余规则一字不改。

### 0.2 标注约定

- **占位符**（如 `<子仓库>`、`<厂商库目录>`、`<IDE>`、`<MCU>`）：正文通用规则一律使用占位符，禁止写死工程名，各工程按实际值对应
- **固定目录名**（如 `01.HAL`）：为保持跨工程统一而约定的固定名称，各工程必须使用同名目录，不得改名，因此正文直接写出、不作参数化
- **（示例）**：纯说明性举例，不构成对当前工程的约束

## 1. 适用范围

适用于基于官方外设驱动库的 C 语言嵌入式项目，使用 Git 管理，支持**主仓库 + 子仓库**与**单仓库**两种形态（见第 0.1 节）。

核心目标：**HAL 作为主仓库与上层模块的硬件抽象边界，DRV/BSP/APP 与具体 MCU 隔离，实现跨产品代码最大程度复用。**

---

## 2. 总体架构

```text
主工程/
├── <厂商库目录>/              ← 官方库 (CMSIS + 外设驱动库)
├── 01.HAL/                    ← MCU 硬件抽象层 (主仓库维护，固定目录名，见 0.2)
│   ├── inc/
│   └── src/
├── <子仓库>/                  ← DRV/BSP/APP 所在目录
│   ├── inc/                   ←   形态A: Git Submodule (独立仓库)
│   └── src/                   ←   形态B: 主仓库内普通模块目录
└── <IDE工程目录>/
```

软件依赖（严格单向）：

```text
APP → BSP → DRV → HAL → 厂商官方库 → MCU
```

| 层级 | 职责 | 一句话 |
|------|------|--------|
| HAL | MCU 硬件抽象 | MCU 怎么操作 |
| DRV | 具体芯片/器件驱动 | 芯片怎么操作 |
| BSP | 当前产品硬件封装 | 硬件怎么组织 |
| APP | 产品业务逻辑 | 功能怎么实现 |

## 3. 命名规范

### 3.1 文件名前缀（区分层级）

| 层级 | 文件前缀 | 示例 |
|------|----------|------|
| HAL | `hal_` | `hal_uart.c` |
| DRV | `drv_` | `drv_mpu6050.c` |
| BSP | `bsp_` | `bsp_battery.c` |
| APP | `app_` | `app_parse.c` |
| 公共 | `cfg_` | `cfg_modules.h` (层级无关配置头, 各层均可包含) |

### 3.2 接口名前缀（CamelCase）

| 层级 | 接口前缀 | 示例 |
|------|----------|------|
| HAL | `Hal` | `HalUartInit()` |
| DRV | `Drv` | `DrvMpu6050GetData()` |
| BSP | `Bsp` | `BspBatteryCurrentGet()` |
| APP | `App` | `AppParseProcess()` |

### 3.3 变量命名

| 变量类型 | 命名规则 | 示例 |
|----------|----------|------|
| 全局变量（含 static 文件级变量） | `G_` + PascalCase | `G_SystemTick`、`G_RxBuf` |
| 局部变量 | PascalCase（大驼峰） | `DataLen`、`RecvCount` |
| 结构体类型 | PascalCase + `_S` | `HalUartRxBuffer_S` |
| 结构体指针类型 | `p` + PascalCase + `_S` | `pHalUartRxBuffer_S` |
| 结构体变量 | PascalCase | `HalUartRxBuffer` |
| 结构体指针变量 | `p` + PascalCase | `pHalUartRxBuffer` |
| 枚举类型 | PascalCase + `_E` | `RunFreCtrl_E` |
| 枚举成员 | `层级_` + UPPER_SNAKE_CASE | `HAL_UART_1`、`RUN_100Hz` |

结构体 typedef 必须同时定义类型和指针类型：

```c
typedef struct
{
    unsigned char buf[HAL_UART_RX_BUF_SIZE];
    unsigned int  head;
    unsigned int  tail;
    unsigned int  count;
} HalUartRxBuffer_S, *pHalUartRxBuffer_S;
```

枚举定义示例：

```c
typedef enum
{
    HAL_UART_1 = 1,
    HAL_UART_2,
    HAL_UART_3
} HalUartPort_E;
```

### 3.4 规则

- 文件名：全小写 + 层级前缀，如 `drv_ina226.c`
- 函数名：CamelCase + 层级前缀，如 `DrvIna226Init()`
- 全局变量必须以 `G_` 开头，如 `G_SystemTick`；static 文件级变量同样以 `G_` 开头（不区分是否 static）
- 结构体类型以 `_S` 结尾，枚举类型以 `_E` 结尾
- 指针类型加 `p` 前缀，如 `pHalUartRxBuffer_S`
- 文件名和接口名必须同时体现层级

### 3.5 函数注释规范（Doxygen）

子仓库中**所有函数（含 `static` 内部函数）**的定义上方必须有 Doxygen 风格中文注释块，格式统一：

```c
/**
 * @brief 一句话功能说明
 * @param 参数名 参数含义说明（含取值范围/单位/格式）
 * @retval 返回值说明（各返回值含义）
 * @note 注意事项
 */
```

#### 3.5.1 标签必填规则

| 标签 | 必填条件 | 内容要求 |
|------|----------|----------|
| `@brief` | 所有函数必填 | 一句话说明"做什么"；禁止写"无"/"略" |
| `@param` | 有参数的函数必填 | 逐参数一行，写明取值范围、单位或格式（如 `0~127, 单位像素`、`"%d"/"%.1f"格式串`） |
| `@retval` | 非 `void` 函数必填 | 写明各返回值含义（如 `0成功 -1失败`、`BSP_WIFI_OK/BSP_WIFI_ERROR`）；`void` 函数省略本行 |
| `@note` | 存在下表任一场景时必填 | 无注意事项的简单函数可省 |

#### 3.5.2 `@note` 必填场景

| 场景 | 注释示例 |
|------|----------|
| 阻塞/耗时 | `最坏阻塞约15s，勿在中断中调用`、`I2C整屏刷新约10ms` |
| 超时与重试 | `重试3次，单次超时15s` |
| 调用前置条件 | `须在Init后调用`、`须先Attach绑定引脚，否则写操作被忽略` |
| 调用周期/上下文 | `必须在1ms定时中断中调用`、`1Hz主循环轮询调用，不可重入` |
| 缓冲区限制 | `输出缓冲区至少InLen*2+1字节`、`payload超长自动截断` |
| 副作用 | `写入前自动整页擦除，同页旧数据一并清除` |
| 仅写显存类 | `仅写显存，需调用Refresh后屏幕才更新` |
| 引脚/资源风险 | `PA13/PA14为SWD调试口，黑名单拒绝绑定` |

#### 3.5.3 检查方法

逐文件扫描 `<子仓库>/src/*.c` 中每个函数定义（正则 `^[a-zA-Z_][a-zA-Z0-9_ \*]*\([^;]*\)\s*$` 定位），向上回溯确认紧邻的注释块：

1. 缺 `/**` 注释块 → 判定**缺函数说明**
2. 有注释块但缺 `@brief` 或内容敷衍（"无"/"略"）→ 判定**说明不合格**
3. 函数命中 3.5.2 任一场景但缺 `@note` → 判定**缺注意事项**
4. 有参数但缺 `@param`、非 `void` 但缺 `@retval` → 判定**参数/返回值未标注**

输出格式：`文件名:行号 函数名 缺失项` 清单，全部修复后方可通过 Code Review。

### 3.6 函数实现长度规范

单个函数的功能实现**尽量控制在 10~20 行**（不含注释与空行），太长会影响阅读与维护。

- 超过 20 行时，优先按功能拆分为职责单一的子函数（如状态机各分支、初始化/收发/保活各环节独立成函数）
- 拆分后每个子函数同样遵循本规范；查表、长 `switch-case` 分发等结构性代码可适当放宽
- 拆分收益：主流程一眼可读，子函数可独立测试与复用

检查方法：扫描各函数 `{` 与配对 `}` 之间的有效代码行数，超过 20 行的函数列出清单逐个评估；确无拆分边界的，在函数注释 `@note` 中说明保留原因。

## 4. 目录设计

### 4.1 子仓库统一 inc/src 结构

子仓库内部**不按软件层级建目录**，统一使用 `inc/` + `src/`，通过文件名前缀区分层级。

禁止：

```text
<子仓库>/
├── APP/
├── BSP/
└── DRV/
```

正确：

```text
<子仓库>/
├── inc/
│   ├── app_main.h
│   ├── bsp_sensor.h
│   └── drv_mpu6050.h
└── src/
    ├── app_main.c
    ├── bsp_sensor.c
    └── drv_mpu6050.c
```

### 4.2 为什么用 inc/src 而非分层目录

1. 目录结构简单，模块增加不产生目录膨胀
2. 文件名前缀已能明确层级
3. IDE 工程直接配置 `src/*.c` + `inc/` 即可
4. 搜索 `drv_` / `bsp_` / `app_` 可快速定位同层所有文件

## 5. 各层职责

### HAL（主仓库）

负责：GPIO、UART、I2C、SPI、CAN、ADC、PWM、TIMER、DMA、EXTI、FLASH、RTC、NVIC、SysTick 等 MCU 外设。

**不负责**：传感器业务、产品逻辑、协议解析、状态机。

HAL 是主仓库与 `<子仓库>` 的接口边界，上层模块只依赖 HAL 抽象接口，不依赖具体 MCU 型号。

### DRV

负责：具体芯片初始化、寄存器配置、通信、原始数据读取与转换。

例如：`drv_mpu6050`、`drv_ina226`、`drv_sht3x`、`drv_oled`、`drv_ml307`（示例）

**DRV 只能通过 HAL 访问 MCU 硬件，禁止直接操作寄存器或外设指针。**

### BSP

负责：当前产品硬件资源与 DRV 之间的组合、封装和适配。

例如：`bsp_battery`（调用 `drv_ina226`）、`bsp_sensor`（调用 `drv_mpu6050`）（示例）

### APP

负责：产品功能、状态机、数据处理、故障处理、通信等业务逻辑。

**APP 通过 BSP 访问硬件，不直接调用 DRV 或 HAL。**

## 6. 依赖规则

```text
允许：  APP→BSP   BSP→DRV   DRV→HAL
        任意层→cfg_modules.h (层级无关编译配置头, 只含宏开关)
        任意层→HAL公开类型 (仅类型引用豁免: 上层对外接口可用HalGpioPort_E、
        串口号枚举等HAL公开类型作参数, 类型引用不构成跳层调用依赖;
        仍禁止调用Hal*函数或依赖HAL内部实现)

禁止：  APP→DRV   APP→HAL   BSP→HAL   BSP→APP
        DRV→BSP   DRV→APP   HAL→任意上层
```

### 6.1 调用链示例

```text
AppBatteryProcess()
    ↓
BspBatteryCurrentGet()
    ↓
DrvIna226GetCurrent()
    ↓
HalI2cRead()
    ↓
I2C 外设 → INA226
```

## 7. 新增代码层级判断

| 代码内容 | 所属层 |
|----------|--------|
| GPIO/UART/I2C/SPI/ADC/PWM/TIMER/FLASH 操作 | HAL |
| 具体芯片寄存器操作（MPU6050/INA226/SHT3X/OLED） | DRV |
| 产品硬件描述（电池电压、设备温度、产品按键） | BSP |
| 产品功能逻辑（电池管理、传感器融合、服务器通信） | APP |

**反例**：DRV 中写低电量判断/充电控制/上传服务器 → 应放 APP。APP 中直接 `I2C_SendData()` → 应通过 BSP→DRV→HAL。

## 8. HAL 接口稳定性

HAL 接口一旦确定，不应频繁修改函数原型。扩展时优先：增加参数、增加新接口、增加配置结构体，保留旧接口兼容。

HAL 禁止直接操作（示例）：

```c
GPIOA->ODR    I2C1->DR    USART1->DR    TIM2->CNT
```

这些操作必须封装在 HAL 中，对上层透明。

## 9. MCU 迁移

更换 MCU（如 STM32F103 → GD32F303，示例）时，**原则上只需修改 HAL**，DRV/BSP/APP 尽可能不变。

### 9.1 迁移原则

- 子仓库通过 `Hal*()` 抽象接口访问硬件，不直接依赖任何 MCU 厂商头文件
- 移植的核心任务是在主仓库中用新 MCU 的 SDK 重新实现 HAL 层接口
- 子仓库的 HAL 接口清单、移植步骤和检查清单见 `<子仓库Readme>` 的「MCU移植指南」章节

### 9.2 迁移阶段

```
阶段1: HAL重建 (主仓库)     — 新建工程/替换官方库/重新实现HAL接口/配置SysTick
阶段2: 子仓库集成            — 引入<子仓库>(形态A:Submodule/形态B:模块目录)/配置编译/确认零厂商头文件依赖
阶段3: 硬件适配 (子仓库)     — 调整BSP引脚分配/调整APP层参数
阶段4: 验证                  — 编译/MAP分析/烧录测试/更新文档
```

### 9.3 迁移检查项 (Code Review)

- [ ] 子仓库零直接依赖 MCU 厂商头文件（无厂商 `xxx.h` 直接包含）？
- [ ] 子仓库无直接寄存器操作（无 `外设->` 形式）？
- [ ] HAL 层接口已按 `<子仓库Readme>`「MCU移植指南」清单全部实现？
- [ ] `<子仓库Readme>`「MCU移植指南」检查清单已逐项确认？

## 11. 内存与中断规范

### 内存

- 优先使用 `const`、`static`、固定长度 Buffer、RingBuffer
- 减少/避免全局 Buffer 和重复 Buffer
- 原则上不使用 `malloc/free`

### 中断

中断中只做：读取必要数据 → 写入 Buffer → 设置标志 → 退出。

**禁止**在中断中执行：长时间循环、阻塞等待、协议解析、大量 printf、浮点计算、长延时。

## 12. 编译资源检查（MAP 文件分析）

### 12.1 检查方法

每次编译后，`<IDE>` 在输出目录生成 `.map` 文件。打开 MAP 文件末尾，找到以下三行：

```text
Total RO  Size (Code + RO Data)                XXXXX (  XX.XXkB)
Total RW  Size (RW Data + ZI Data)             XXXXX (  XX.XXkB)
Total ROM Size (Code + RO Data + RW Data)      XXXXX (  XX.XXkB)
```

### 12.2 字段说明

| MAP 字段 | 含义 | 对应 MCU 资源 |
|----------|------|--------------|
| Total RO Size | Code + RO Data（只读代码+常量） | 占用 Flash |
| Total RW Size | RW Data + ZI Data（已初始化+未初始化变量） | 占用 SRAM |
| Total ROM Size | Code + RO Data + RW Data（实际烧写到Flash的总量） | 占用 Flash |

> **RW Data** 会被存储在 Flash 中，启动时搬运到 SRAM，因此同时占用 Flash 和 SRAM。

### 12.3 判定规则

将 MAP 文件中的实际占用与所选 `<MCU>` 的实际 Flash / SRAM 容量对照：

```
Flash 占用 = Total ROM Size
SRAM 占用  = Total RW Size

Flash 使用率 = Flash 占用 / MCU Flash 总量 × 100%
SRAM 使用率  = SRAM 占用  / MCU SRAM 总量 × 100%
```

| 状态 | 条件 | 处理 |
|------|------|------|
| ✅ 正常 | Flash < 80% 且 SRAM < 80% | 无需操作 |
| ⚠️ 警告 | Flash ≥ 80% 或 SRAM ≥ 80% | 优化代码体积/内存占用 |
| 🔴 危险 | Flash ≥ 95% 或 SRAM ≥ 95% | 必须优化，否则无法继续开发 |

**弱符号兜底检查（条件项）**：若工程使用了弱符号兜底文件（如 `hal_stub.c`，为全部 HAL 公开接口提供 `__weak` 空实现/错误码实现），正式构建后检查 MAP 中该文件应**无存活符号**——出现存活符号即说明存在"被上层引用但 HAL 未实现"的接口，需补齐实现或裁剪上层功能开关。HAL 全实现时兜底文件被强符号覆盖剔除，Flash 占用为 0。维护纪律：HAL 新增公开接口须同步兜底文件补 stub。

> 编译结果是随每次构建变化的项目数据，**不记录于本模板**；如需留存历史趋势，记录到 `<主仓库Readme>` 等工程自有文档，避免模板被逐次修改。

## 13. 功能记录维护

### 13.1 记录规则

每实现一个新功能，必须同步更新对应范围的 Readme：

| 范围 | 文件 | 记录范围 |
|------|------|----------|
| 主仓库 | `<主仓库Readme>` | HAL 层功能（UART/Timer/GPIO/ADC/SPI/I2C 等） |
| 子仓库 | `<子仓库Readme>` | BSP/DRV/APP 层功能（串口封装/解析/调度/驱动等） |

形态B（单仓库）下，两份记录合并为同一 Readme 的两个章节，记录范围与更新规则不变。

### 13.2 记录格式

每个模块按统一格式记录：

```markdown
### 模块名

| 功能 | API | 说明 |
|------|-----|------|
| 功能A | `FuncA()` | 简要说明 |
| 功能B | `FuncB()` | 简要说明 |
```

### 13.3 更新时机

1. 新增 HAL/BSP/APP 接口时
2. 修改已有接口原型时
3. 删除接口时
4. Code Review 前确认记录已同步

### 13.4 Code Review 补充检查项

- [ ] 主仓库 Readme 已同步 HAL 新增功能？
- [ ] 子仓库 Readme 已同步 BSP/DRV/APP 新增功能？
- [ ] 每个硬件号的数据流转图已同步更新？（第 13.5 节）

### 13.5 硬件号数据流转

子仓库 Readme 必须为**特性表登记的每个硬件号**维护**两份材料**：

1. **数据通路清单表**（主）—— 逐条通路，一表看全"源→采集→缓存→消费→输出"
2. **分阶段流程图**（辅）—— Mermaid `flowchart LR`，按五阶段分组

**通路阶段模型**（所有硬件号统一）：

```
①输入源 → ②采集/解析(BSP·DRV·APP) → ③数据缓存/命令 → ④决策(APP) → ⑤输出
```

**清单表格式**（每条通路一行，通路编号 P1/P2... 与图中边标注对应；下表为格式示例）：

```markdown
| 通路 | ①输入源 | ②采集/解析 | 触发·频率 | ③数据落点 | ④消费方 | ⑤输出 |
|------|---------|-----------|----------|----------|---------|-------|
| P1 避障 | HC-SR04(PB5/PB6) | app_func 阻塞测距 | 10Hz槽 | DistCm缓存 | app_car 避障状态机 | 电机+舵机 |
| P3 语音 | 语音模块(UART2) | AppCarVoiceRxIsr置码 | RXNE中断→10Hz消费 | G_VoiceCmd | app_car | 电机+舵机 |
```

**流程图要求**：

1. 五个 subgraph 按阶段命名：`①输入源`/`②采集/解析`/`③数据缓存/命令`/`④决策`/`⑤输出`
2. 每个节点标注：所属模块（层前缀）+ 引脚/串口 + 频率或触发方式
3. 边标注通路编号（P1/P2...）与数据内容；**虚线 `-.->` = 中断直达，实线 `-->` = 主循环轮询/阻塞**
4. 数据左进右出：输入源在最左，物理输出在最右，天然无回边交叉

**多硬件号差异速览表**（硬件号≥2 时必填；下表为格式示例）：

```markdown
| 维度 | C000 | C001 |
|------|------|------|
| 主动采集源 | ... | ... |
| 中断链 | ... | ... |
| 闭环决策 | 无(指令直控) | app_car状态机 |
```

**更新时机**（任一触发即须更新清单表+图）：

- 特性表功能位或串口字段变化
- 新增/删除模块
- 采样频率槽调整（如超声波 10Hz → 20Hz）
- 中断回调注册关系变化

**检查要点**（Code Review 时逐项核对）：

- [ ] 清单表通路集合与特性表该行功能位/串口字段一致（无多画/漏画）？

- [ ] 中断链（虚线）与主循环链（实线）区分标注？触发方式（中断/轮询/阻塞/AT按需）写实？
- [ ] 频率槽标注与 `app_main.c` 的 `AppProcess` 调度表一致？

## 15. 架构总则

> 主仓库只维护 HAL，DRV/BSP/APP 集中在 `<子仓库>`（形态A 为 Submodule，形态B 为仓库内模块目录）。
> 子仓库统一 `inc/src` 目录，通过 `hal_/drv_/bsp_/app_` 文件名前缀和 `Hal/Drv/Bsp/App` 接口前缀区分层级。
> 严格遵循 `APP → BSP → DRV → HAL` 单向依赖，软件层级通过文件名、接口名和调用关系体现，不通过目录体现。
> 本文档为通用模板，工程差异通过占位符体现，复制到任意新工程无需任何修改。
