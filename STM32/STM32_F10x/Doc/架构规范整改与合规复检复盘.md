## 整改内容与修复模式 (5 项)

### 1. APP→HAL 直调 → DRV 薄转发层

**违规**: USB CDC 移植时 `app_parse.c`/`app_main.c` 直接调用 `HalUsbSend/HalUsbReceive/HalUsbInit` (APP 层禁止直调 HAL 函数, 类型引用豁免除外)。

**修复模式 — 同签名薄转发**: 新建 `drv_usb.h/.c`, 五接口 `DrvUsbInit/Connected/Receive/RxAvailable/Send` 一律 `return HalUsb*(同参);`。转发层零逻辑, 固件尺寸零增长。**教训**: 移植厂商参考工程时, 其示例代码直调 HAL 的路径必须套一层 DRV 封装才能进 APP。

**坑**: `drv_usb.c` 编译开关守卫 `#ifdef APP_MOD_USBCDC` 需要 `cfg_modules.h` 先行 include, 否则宏不可见 → 整文件被预处理器裁空 → 链接期 `Undefined symbol`。模块开关宏的可见性必须从 `.c` 第一个 include 开始保证。

### 2. BSP→DRV 反向依赖 → 节拍钩子注册

**违规**: `bsp_board.c` include `drv_esp01s.h` 并在 SysTick 内直调 `DrvEsp01sTick()`, 且承担器件初始化 (规范: BSP 禁止调用 DRV/APP)。

**修复模式 — 回调注册 (规范 §11)**: 上层向下层注册函数指针, 注册动作本身是合法向下调用, 运行时反演不构成依赖违规:

```c
/* app_main.c AppBaseInit (上层) */
DrvSysTickCbSet(BspSysTickMs);            /* APP→DRV 注册节拍回调 */
#if APP_MOD_ALIYUN || APP_MOD_BEMFA || APP_MOD_ONENET
    BspSysTickHookRegister(DrvEsp01sTick); /* APP→BSP 注册扩展钩子 */
#endif
DrvSysTickInit(1000);                      /* 钩子必须在节拍启动前注册 */
```

`bsp_board.c` 内仅 `static void (*G_SysTickHook)(void) = 0;` + 判空调用, 零 include 反向依赖。器件初始化上移为 `app_main.c` 的 `AppBaseInit()` (Flash/SysTick/UART1 经 DRV 层), `BspBoardInit()` 直接删除 —— 本工程无板级上电时序需求 (时钟由 `SystemInit` 完成), 不留空壳函数。

**设计决策**: ESP01S tick 留在中断内不迁主循环 —— 云平台 AT 阻塞等待依赖该 tick 计时, 移走会停摆。

### 3. 厂商库目录位置 → 移出 HAL 层

**违规**: ST 官方 USB 库 `usb_st/` 位于 `01.HAL/` 下 (HAL 层应只含自研硬件抽象)。

**修复**: 整体迁移 `01.HAL/usb_st → 00.STM32/USB_ST_LIB` (与 StdPeriph_Driver/CMSIS 同级的厂商库区), uvprojx IncludePath + 12 处 FilePath + uvoptx 同步。**原则**: 第三方厂商代码不参与自研分层, 单独归区。

### 4. 命名修复与厂商契约豁免

- 模块级变量补 `G_` 前缀: `DrvEsp01sIpdTag→G_Esp01sIpdTag`, `uu_txfifo→G_UsbTxFifo`, `_usb_usart_fifo→HalUsbFifo_S`
- **豁免先例**: libc 钩子 `_sys_exit`/`fputc` 按函数名契约被工具链调用, 同理 `USBCableConfig`/`EnterLowPowerMode`/`LeaveLowPowerMode` 被 ST `usb_pwr.c` 按名调用, 豁免 `Hal` 前缀但必须在 Doxygen `@note` 写明豁免依据
- GBK 文件改名用 Latin-1 (ISO-8859-1) 1:1 字节映射做 ASCII 标识符替换, 中文字节原样保留

### 5. 注释欠账清偿

- 全工程 Doxygen 函数注释块缺失清零 (1103 个自研函数 0 缺失)
- 超 50 行函数 16 个补 `@note` 保留原因 (规范 10-20 行, 对查表/switch 多分支/机型初始化序列/OLED 绘制/AT 回调解析放宽, 逐个注明超长类型)
- 顺带修复全量编译暴露的既有死代码告警: `app_cloud.c` 三云全关时 `printf` 三行不可达 (原 `#else` 分支已 `return`), 加云使能守卫行为零变化

## 复检方法论教训

1. **AI 审查报告数字必须实查复核**: 上轮审查报「1013 处 Doxygen 缺失 + 190 个超长函数」, 精确扫描 (正则定位函数定义行 + 回溯 `/**` 注释块 + 花括号计数函数体) 实查仅 **28 处 + 16 个** —— 审查代理的宽口径统计不可直接采信, 整改前必须产出带文件+行号的精确清单。
2. **增量编译掩盖真实告警**: 基线「0 警告」可能只是没重编出问题的文件 (`app_cloud.c` 死代码告警在结构整改轮从未现身, 规范整改轮全量重编才暴露)。验收必须 Rebuild 全量。
3. **多代理并行的编码风险**: 3 个并行子代理用 Edit 工具改注释, 全部触发文件整体转码 (详见编码陷阱文档), 代理自检「渲染正常」不可靠, 必须主会话字节级复检 (git diff 逐行核对)。
