# GD32F470 串口 Bootloader 非均匀扇区分区设计与跳转失败修复报告（2026-11-23）

> 涉及工程：GD32F4xx_Loader（Loader 固件 + bsp_loader 升级框架子仓库）/ GD32F4xxMCU（APP，BSP_501_PROJECT / HARDWARE_501_D00）
> 芯片：GD32F470ZGT6（1MB Flash 单 Bank 12 扇区，**非均匀扇区** 4×16KB + 64KB + 7×128KB，最小擦除粒度 16KB，晶振 25MHz / 主频 200MHz）
> 关联文档：[GD32F103/量产Loader升级SN丢失与参数页安全迁移报告](../GD32F103/量产Loader升级SN丢失与参数页安全迁移报告.md)（页擦除平台的参数页设计，本报告为其在扇区擦除芯片上的对照与延伸）

## 一、问题现象

分别烧录 Loader 与 APP 后无法从 Loader 跳转到 APP：上电永远停留在 Loader，升级窗口期内
AT+VERSION? 正常应答（LoaderVersion V1.0.0.4）、AT 协议完全正常——表象是"业务正常待升级"，
实际是 **BootCount=3 的永久待升级状态**，与升级框架自身的校验失败连锁有关。

## 二、根因分析

### 2.1 直接根因：平台宏缺失落入占位配置，擦参数区毁掉 APP 向量表

升级框架多平台共用一份 `bsp_config.h`（按编译宏切换平台分支）。GD32F470 分支缺失时落入了
**1KB 页擦除芯片的占位配置**：参数区 0x08004000、APP 基址 0x08006000。两个地址在 F103/F303
页擦除芯片上是不同页、互不影响；但在 GD32F470 上**同驻扇区1（16KB 整扇区擦除）**：

```text
上电 AppUpgradeInit() 发现参数区无效 → 擦"参数页" → 实际整扇区 16KB 连 APP 向量表(0x08006000)一起擦毁
→ AppUpgradeAppValidate() 校验失败 → BootCount++ → 3 次后置永久待升级 → AT 仍应答（Loader 活着）
```

**教训：页擦除假设（"擦参数不影响 APP"）隐式依赖擦除粒度，换扇区芯片时整条地址规划失效，
而编译照常通过——占位配置是定时炸弹。**

### 2.2 次生根因（修复过程中连环暴露）

| 问题 | 说明 |
|------|------|
| 同扇区元数据一致性 | 参数区与 APP 标志位同扇区时，任一处写入必须整扇区重写（MetaSync 统一擦写），否则写参数毁标志、写标志毁参数 |
| 整区擦除步进错误 | 按固定页大小步进的擦除循环在非均匀扇区芯片上会擦错位置，必须按扇区边界表步进 |
| APP_END 与 APP 参数页重叠 | 升级整区擦除上界一度覆盖 APP 参数页（扇区5/6），必须收缩 APP_END 且升级入口校验固件总长 |
| APP 工程三处地址失同步 | VTOR 偏移宏、Keil IROM1 链接基址、命令行 --ro-base 三处必须一致，漏一处即跳转后中断取向量错误 |
| 旧参数残留污染 | 布局变更后旧布局的 BootCount=3 残留在原地址，新 Loader 若元数据地址未变会直接继承"永久待升级"状态 |

### 2.3 布局演进（三个版本）

```text
v1  参数+标志同扇区1（MetaSync 统一擦写），APP=0x08008000, 固件区 96KB
     ↓ 用户要求 APP 前移
v2  参数+标志迁末尾独立扇区，APP=0x08006000, 固件区 872KB（APP_END 0x08020000 未改时与参数页重叠）
     ↓ 回归"参数+标志独立成扇区"方案
v3（最终）标志/参数各占独立扇区，APP=0x0800C000, 固件区 80KB, APP_END=参数页之前
```

## 三、最终布局与关键实现

### 3.1 GD32F470ZGT6 分区表（v3 最终）

| 地址范围 | 区域 | 扇区 | 说明 |
|----------|------|------|------|
| 0x08000000~0x08003FFF | Loader 代码区（实测 12.0KB） | 扇区0(16KB) | Code 10692+RO 1588+RW 40 |
| 0x08004000 | APP 存在标志位（0x5A5A5A5A） | 扇区1(16KB) | 独立扇区，仅用首 4 字节 |
| 0x08008000 | Loader 参数区（FlashInf_S 24B） | 扇区2(16KB) | 独立扇区，BootCount/版本/日期 |
| 0x0800C000~0x0801FFFF | APP 固件区（80KB） | 扇区3~4 | APP_START/APP_END=升级擦除上界 |
| 0x08020000 / 0x08040000 | APP 参数页 A/B | 扇区5/6(128KB×2) | APP 所有，升级擦除不波及 |
| 0x08060000~0x080FFFFF | 预留 | 扇区7~11 | 升级擦除不波及 |

### 3.2 设计原则（升级框架侧）

1. **元数据独立扇区**：代码/标志/参数各占独立擦除单元，擦写互不影响。页擦除平台（F103/F303，
   参数/标志不同页）天然满足；扇区芯片必须显式规划。独立后 MetaSync 统一擦写逻辑整体删除，
   全平台回归同一套独立擦写代码（无平台分支）。
2. **APP_END 即升级擦除上界**：`AppUpgradeStart()` 校验固件总长不超分区（超限直接应答失败，
   防越界写毁参数页）；整区擦除与 APP 校验边界同步受 APP_END 约束，上限由地址宏自动推导。
3. **扇区遍历擦除**：`DrvFlashNextSectorAddr()` 按 16K/64K/128K 实际边界步进（12 扇区地址表）。
4. **首烧自愈**：标志位无效但固件校验通过（SWD 单烧 APP 场景）→ 自动补写标志 → 清 BootCount
   → 开等待窗口跳转，无需烧录脚本补写标志。
5. **跳转加固**：`HalChipAppJump` 跳转前关全局中断+停 SysTick+清挂起；APP 启动首行
   `HalVtorSet(BSP_APP_FLASH_OFFSET)` 重映射向量表。

### 3.3 APP 工程同步三处（换基址必改清单）

| 文件 | 内容 |
|------|------|
| `02.Application/inc/bsp_config.h` | `BSP_APP_FLASH_OFFSET 0xC000U`（VTOR 重映射取此宏） |
| `projects/Project.uvprojx` | IROM1 `StartAddress 0x800C000 / Size 0xF4000`（链接区到芯片末尾） |
| `projects/build_ac5.ps1` | `--ro-base=0x0800C000`（命令行编译同步） |

自检方法：hex 首行应为 `:10C00000 <栈顶4B> <复位向量4B>`（如 `00230020 C5C10008`——栈顶
0x20002300、复位向量 0x0800C1C5 带 Thumb 位）。

Loader 侧 Keil 工程同样四处一致：Device（GD32F470ZG）、Flash 算法（GD32F4xx_1MB/FL0100000）、
IROM 容量（0x100000）、编译宏（GD32F470ZGT6,GD32F470——完整型号供平台分支、系列宏供 gdlib）。

### 3.4 编译与验证

- Loader：0 错 0 警，Code+RO+RW ≈ 12.0KB（扇区0 内，余量约 4KB）
- APP：0 错 8 警（均为遗留未引用变量警告），ROM 共 38.3KB（80KB 上限内，接入算法库后余量 40KB+）
- 升级链路自检：BootCount/标志/参数写入只擦各自扇区；升级整区擦除扇区遍历 0x0800C000→0x0801FFFF，
  元数据与参数页不波及

## 四、烧录与恢复纪律

1. **布局变更后必须 Full chip erase 一次再重烧两个工程**——旧布局残留参数（如 BootCount=3）会污染
   新状态机；日常烧录用 Erase Sectors。
2. 卡 Loader 诊断顺序：`AT+FLASHINFO?` 看 AppExist → 查 APP hex 首行链接地址是否等于 APP_START
   → 查是否继承旧 BootCount 残留（升级完成指令 CMD 0x05 可清）。
3. 布局迭代期间上位机不感知地址变化（协议不含地址），但 AppExist 标志位置变化后旧上位机脚本里的
   地址硬编码需同步。

## 五、教训沉淀

1. **换芯片先核对四件事**：平台宏分支是否存在、擦除粒度（页 vs 扇区）、元数据与代码区是否共用擦除
   单元、Keil 器件/Flash 算法/IROM/宏四处一致。任何一项错位都可能"编译通过但运行毁数据"。
2. **占位配置必须保守**：默认分支宁可宏报错编译失败，不可静默落入错误擦除粒度的地址规划。
3. **页擦除假设要显式化**：凡依赖"擦 A 不影响 B"的地址规划，都应写成"擦除单元隔离"的显式约束
   （独立扇区/独立页），而不是隐式依赖当前芯片的粒度巧合。
4. **多平台共用的分区配置**，换平台时逐项对照擦除粒度重推地址，不能只改容量数字。
