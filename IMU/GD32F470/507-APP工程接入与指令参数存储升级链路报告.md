# 507 APP 工程接入与指令/参数存储/升级链路报告

> 工程背景：GD32F4xxMCU 共用工程新接入 507 产品（GD32F470ZGT6，APP 基址 0x0800C000）。
> 507 初期暂无算法计算（传感器+算法库不初始化），仅保留指令解析/配置/推送框架；
> 本报告记录宏接入模式、三件套（指令回复/参数存储/固件升级）接入与踩坑。

## 1. BSP_507_PROJECT 宏接入模式（其它产品零影响保障）

- 共用工程惯例：每个产品一个**独立并列 `#if defined(BSP_xxx_PROJECT)` 块**（不级联 #elif）。
  507 接入全部为并列新增分支；其它产品不定义 507 宏 → `|| defined(BSP_507_PROJECT)` 恒假 →
  预处理逐字节等价，零影响可静态论证。
- bsp_parse.c / bsp_protocol.c 等协议层无 501/507 专属 guard，507 走 `#else` 通用路径
  （与量产 501 同路径）——AT/HEX 双指令协议层直接继承可用。
- **不建议把并列块改成级联 #if/#elif/#else**：现有 `#else`/`#elif` 分支承载"其余所有产品"
  的公共声明（如 351 块 #else 的 BspDrvUsTimeSourceInit 声明、501 块 #elif 的 BMM350_ADDR
  fallback），级联后公共内容失去落点，必须逐分支复制或挪链外，收益小回归大。

### 算法链摘除（507 暂无算法计算的边界）

- 摘除的是**调用/初始化层**：`#if !defined(BSP_507_PROJECT)` 包裹 BspAppLoopAlgorithmTask
  整体与 app_main.c 的 BspAlgorithmInit() 调用；bsp_algorithm.c 本身零改动（507 分支保留为
  恢复点，不调用即死代码被链接器剔除）。
- 配置/协议路径（bsp_parse/bsp_protocol/bsp_data_interaction 的指令与配置）**仍编译**，
  推送框架正常（数据内容为 0）。

## 2. 教训：发送链 guard 漏分支 → 指令回复静默丢帧

**现象**：507 收到 0x0603（查询信息）后上位机看不到任何回复，但指令解析、组包（SN/版本/
升级时间/型号）全部正常。

**根因**：`BspParseSendData` 的发送条件链只有 351/303_333/335/506 四个分支，507 不在链中
——最后发送调用是**空操作**，回复帧被静默丢弃。无报错、无日志，极易误判为"指令没收到"。

**修复**：发送链并列加 `#elif defined(BSP_507_PROJECT)` → UART0SendData；同时 0603 的
版本字节 guard 加 507（否则回复中库/APP 版本 8 字节全 0）。

**通用教训**：新增产品宏后，凡 `#if 产品A || 产品B` 型条件链（发送、版本、校准等）都要
排查"漏我"——编译器不会提醒，行为是静默降级。

## 3. 参数存储：A/B 双页在 GD32F4 上的布局约束

- 双页冗余机制与 506 完全共用（写非活跃页+Sequence+Crc，掉电必有一份完整配置；读取双页
  CRC 校验取 Sequence 高者）。
- **GD32F470 无小页**：最小擦除单位 16KB 扇区（sector0~3）/128KB（sector4~11），F1/F3 的
  1~2KB 页擦除假设失效。A/B 双页必须放两个独立扇区，取 sector5/6（0x08020000/0x08040000）。
- **保存代价**：每次保存擦一个 128KB 扇区，CPU 停顿约 1~2s（中断与推送冻结）；期间高速
  数据流入可能溢出 1024B 接收队列（低频操作可接受，需知悉）。
- **两条硬约束**（与 loader 布局联动）：
  1. APP 固件 ROM < 80KB（APP 区 0x0800C000~0x0801FFFF；注意 uvprojx IROM1 Size 若设为
     覆盖到片尾，链接器允许固件超界不报错——须编译后检查 HEX 尾址 < 0x08020000）；
  2. loader 升级擦除上界（APP_END）必须 = 0x08020000，否则整区擦除毁参数页。

## 4. 固件升级链路（0604，参照 506）

```
上位机 0604 → APP 回ACK → 参数强制落盘 → 清升级标志 → 复位
→ loader 见标志≠0x5A5A5A5A → 进升级等待 → 收固件→按扇区擦APP区→写固件→写标志→跳转APP
```

- 升级标志：**0x08004000**（sector1 首 4 字节，与 loader GD32F470 分支三方对齐，
  ==0x5A5A5A5A 判 APP 有效）。
- **关键防线——纯字编程接口**：升级标志 0x08004000 与 loader 参数区 0x08008000 前的
  sector1 同扇区，GD32F4 擦除粒度 16KB——若用带"非全 FF 先整扇区擦除"逻辑的通用写接口
  清标志，会连带毁掉同扇区其它数据。新增 `DrvFlashWordProgramNoErase`（不检查不擦除，
  仅利用 F4 1写0 特性编程）。
- `DrvUpgradeChipRest`（参照 303）：清标志 → 延时 2s（上位机收尾）→ NVIC_SystemReset。
- **首烧陷阱**：SWD 只烧 APP 时标志区为 0xFF，loader 上电判"进升级"——首次生产烧录须
  经 loader 烧 APP 或烧录脚本补写标志（loader 升级完成流程自带写入，仅首烧场景需补）。
