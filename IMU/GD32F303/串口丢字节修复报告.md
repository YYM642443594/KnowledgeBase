# 串口丢字节修复报告（2026-10-19）

> 现象：921600bps 连发 AT 指令随机丢字节（0.2%~0.95%）｜根因：SysTick 中断（优先级 0）里的 us 时基换算使用 64 位软件除法，拖长中断逼近 1 字节时间（10.86µs），概率性阻塞 USART0 接收造成溢出｜修复：改 32 位硬件除法（数学等价），72540 字节零丢失
>
> 关联：本次问题正是《0x091时间戳抖动修复报告》选定"SysTick ISR 内时基差值累加"方案时引入的回归——时基源移入 SysTick 的同时，把 DWT 换算的 64 位除法也带进了最高优先级中断。

## 一、测试现象

- 平台：GD32F303CB（Cortex-M4，120MHz），USART0 @ 921600bps，PC 串口工具连发 `AT+VERSION?`（13 字节/条）
- 指令被"抠掉"单个字符且位置随机：`AT+VERSIO?`、`AT+VERION?`、`A+VERSION?`、`ATVERSION?`……
- 丢失率约 0.2%~0.95%，轮次间波动（3575 发丢 34 字节；1014 发丢 2 字节）
- 关键线索：d40b955 之前的版本同样测试从不丢失

## 二、排查路径（按时间序）

1. **驱动与配置比对**：`git diff d40b955^` 确认 USART 驱动、时钟树（120MHz PLL）、波特率分频（误差 +0.16%）、NVIC 分组全部零改动——洗清链路配置
2. **回传法**：RX 中断内把收到的字节原样回发，PC 对比"发送流 vs 回传流"。回传流同样残缺 → 字节确实没被设备正确接收，问题在设备侧；期间观察到一处 R→S 位翻转，一度误导向线级干扰（后判定为独立偶发噪声）
3. **ORE 插桩失效的陷阱**：中断里加 ORE/FERR/NERR 计数，读数恒为 0——**GD32（F1 型 USART）的 ORERR 标志会被"读 STAT0 → 读 DATA"序列自动清除**，而 RX 中断的正常处理路径恰好就是这个序列，标志在计数代码看到之前就被清掉了。教训：插桩计数必须最先快照 STAT0
4. **屏蔽法 A/B 定位**：SysTick 处理链中 d40b955 后唯一新增逻辑是 us 时基累加（71b191c）。只屏蔽它、保留调度与喂狗 → 连发 50089 字节零丢失 → 根因锁定
5. **修复验证**：换 32 位硬件除法、恢复累加 → 连发 72540 字节零丢失 → 闭环

## 三、根因分析

问题代码（`dwt.h`，SysTick 每 1ms 经函数指针调用一次）：

```c
static inline uint32_t dwt_us_from_cycles32(uint32_t diff_cycles) {
    return (uint32_t)(((uint64_t)diff_cycles * 1000000ULL) / (uint64_t)SystemCoreClock);
}
```

因果链：

1. Cortex-M4 **没有 64 位硬件除法**，`(uint64_t)/(uint64_t)` 编译为 `__aeabi_uldivmod` 软件例程（数十轮移位减法），约 400~700 周期，加 Flash 等待周期实际 **4~8µs**
2. SysTick 配置为**抢占优先级 0**，高于 USART0 的 (1,0)——SysTick 可随时打断串口接收中断
3. 921600bps 下 **1 字节时间仅 10.86µs**。SysTick 恰好落在字节接收窗口时，RX 中断被推迟 6~10µs，逼近但通常不超过 10.86µs
4. 边际状态 → **概率性**溢出（RXNE 未及时读走 → ORE → 丢 1 字节），丢失率低且随环境波动，与实测吻合
5. 回传模式下 RX 中断本身更长（内含 TBE 忙等），裕量更小 → 丢失率更高（0.95% vs 0.2%），同样吻合

## 四、修复方案

改为 32 位硬件除法（1 条 UDIV 指令，2~12 周期）：

```c
static inline uint32_t dwt_us_from_cycles32(uint32_t diff_cycles)
{
    return diff_cycles / (uint32_t)(SystemCoreClock / 1000000U);
}
```

数学等价性：`SystemCoreClock` 为整 MHz 时（120MHz、108MHz 均满足），

```
floor(diff × 10⁶ / Fclk) ≡ floor(diff / (Fclk / 10⁶))
```

即 120MHz 下就是 `diff / 120`，与原 64 位算法结果逐位一致，零精度损失。已在头文件加注释禁止回退成 64 位写法。

## 五、验证数据（纯回传模式统计）

| 阶段 | 发送/接收 | 丢失 | 说明 |
|---|---|---|---|
| 修复前 | 3575 / 3541 | 34 字节（0.95%） | 含 1 处位翻转（线级噪声，独立偶发） |
| 修复前 | 1014 / 1012 | 2 字节（0.2%） | 丢失率波动，符合边际时序特征 |
| 屏蔽 SysTick 时基累加 | 50089 / 50089 | **0** | A/B 对照，锁定方向 |
| 修复后（累加恢复） | 72540 / 72540 | **0** | 根因闭环，时基功能保留 |

## 六、经验总结

1. **高优先级中断纪律**：优先级高于串口 RX 的中断里，禁用 64 位乘除（软除法数百周期）、`printf`、double 浮点（M4F 的 FPU 只有单精度）
2. **中断时长预算**：任何可能阻塞 RX 的执行路径，总时长必须显著小于最高波特率下 1 字节时间（921600→10.86µs，460800→21.7µs，115200→86.8µs）
3. **USART 错误标志的自动清除陷阱**：ORERR/FERR 会被"读 STAT0 → 读 DATA"序列顺带清除，中断内插桩计数必须最先快照 STAT0，否则恒为 0 并误导排查
4. **回传法（echo 分流）**：RX 中断内回发收到的字节，PC 对比发送流与回传流，一步二分"链路层 vs 设备软件层"，是串口丢字节问题的高效首查手段
5. **边际时序问题的指纹**：丢失率低（<1%）且轮次间波动、丢失位置随机、与软件负载正相关——见到这种模式优先怀疑"某段代码时长逼近字节时间"
