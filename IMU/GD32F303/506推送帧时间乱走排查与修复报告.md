# 506 推送帧时间乱走排查与修复报告

> 工程：GD32F303MCU（分支 `feature/506Custom` + 子仓 BSP_IMU `develop`），产品 506，硬件 B06
> 现象关联帧：HEX/CAN 推送帧内 `year/month/day/hour/minuter/second` 字段（`BspPushOfOriginalData`，bsp_data_interaction.c）
> 关联文档：《0x091时间戳抖动修复报告.md》（时基源注入架构与增量契约）、《PPS功能实现说明.md》

## 一、现象

推送帧时间字段先后表现为三种异常，层层递进：

1. **时间恒为 1970-01-01 不走**：日历字段全部冻结在初值
2. **补上时间同步后开始走时，但月/日/时/分/秒"乱走"**：数值狂奔且无规律（忽快忽慢），远快于真实时间
3. 时间戳（运行 us 数）同样异常增长

## 二、排查过程（三层递进，前两层为干扰项）

### 第 1 层：时间同步调用丢失（真实问题之一）

比对 351 工程发现：351/303 在主循环每拍调用 `BspSystemTimeSync(BspSysRunTimeGet())` 把运行时间戳同步进日历，唯 506 分支该调用在对齐重构时丢失 → 日历永远停在 1970。补回后时间开始走时（提交 c458933）。

### 第 2 层：64 位撕裂读（理论风险，非本次根因）

时间开始走但乱跳，怀疑 `G_SysRunTime`（unsigned long long）撕裂读：Cortex-M4 的 64 位读/写是两条 32 位指令，SysTick 1kHz 中断写 + 主循环 1kHz 读碰撞时偏差可达 ±2^32 µs ≈ **±71.6 分钟**。加了稳定快照读（前后校验 ms 计数）与单调钳位（5a5b96a / 6fb2098）。

**仍不对**——说明撕裂只是次因。后续复盘：351/303 的时基由 1Hz PPS 中断维护，撕裂窗口天然小；506 是 1kHz SysTick 累加，暴露面大，但基准丢失才是量级性错误。最终该层改动**整体回退**（ae536da），`bsp_run_ctrl.c` 保持与参照工程逐字节一致——共用 BSP 文件不做产品私有改动是本仓库纪律。

### 第 3 层：DWT 时基源丢失增量基准更新（真根因）

按"参照 IMU_303_351 工程逐行比对"指示排查 DWT 链路，发现移植遗漏：

```c
/* 参照工程（正确）                    /* 506 移植版（错误） */
DiffUs = GetUs(NowCycles - LastCycles);  DiffUs = GetUs(CurrCycle - LastCycle);
LastCycles = NowCycles;  /* ← 推进基准 */  /* LastCycle 永远是 0 */
```

SysTick 每 1ms 调一次时基源回调、把返回值累加进 `G_SysRunTime`：

- 漏掉基准推进后，第 n 拍累加的是 **n×1000 µs（上电以来的全量）**而非 1ms 增量 → 总量 = 1000×n(n+1)/2 µs，**二次方增长**
- 实测换算：上电 1 秒日历快进到 00:08:20，上电 1 分钟冲到数十天
- DWT CYCCNT 每 ~35.8 s（120MHz）回绕一次，累加值忽大忽小 → 增速无规律 → 表现为"月日时分秒乱走"

**修复**（98bd391，主仓 app_main.c）：补上 `LastCycle = CurrCycle;`，并在时基源注册后预热调用一次建立首拍基准（对齐参照工程"初始化→预热→注册"顺序）。修复后走时与时间戳均正常。

### 辅助诊断手段（保留）

- **复位源上报**：上电经 RCM 打印复位来源（上电/NRST/看门狗/软件复位），HardFault 处理器先打印标记再死循环——用于排除"程序反复跑飞 + 看门狗复位导致时间归零"的假象链路

## 三、根因总结

| 层级 | 问题 | 性质 | 处置 |
|------|------|------|------|
| 1 | 506 分支丢失 `BspSystemTimeSync` 每拍同步 | 真实缺陷 | 补回（仅 506 宏内） |
| 2 | u64 撕裂读 | 理论风险（351 时基在 1Hz PPS 维护不暴露） | 回退，保持参照原版 |
| 3 | 时基源回调漏推进增量基准 | **真根因** | 补基准推进 + 预热 |

## 四、预防措施

1. **时基源增量契约**：时基源回调每次调用必须推进内部基准（这正是《0x091时间戳抖动修复报告》沉淀的"时基源注入架构"契约）；移植该类回调时与参照工程逐行比对，禁止凭记忆重写
2. **共用 BSP 文件纪律**：`bsp_run_ctrl.c` 等参照工程共用文件不做产品私有改动；产品差异收敛到 `BSP_xxx_PROJECT` 宏隔离的调用点（如 506 的 `BspSystemTimeSync` 注入位置）
3. **排查方法论**：本例前两层修复均"合理但非根因"，最终靠**与参照工程逐行比对**闭环——移植类缺陷优先比对参照，而非只靠推理
4. 64 位变量跨中断/主循环读写时仍需警惕撕裂（±71.6 分钟偏差量级），新平台设计时基时优先评估单写者+快照读或双读重试（103 平台 bsp_pps.c 已有成熟先例）

## 五、验证结论

烧录修复后固件：时间平滑走时（1970-01-01 + 开机时长，506 无 PPS 架构预期），上位机发一次时间设置即显示真实时间；推送帧时间戳单调、与真实时间一致。
