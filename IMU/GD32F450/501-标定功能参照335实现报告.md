# 501 标定功能参照 335 实现报告

> 需求：501（GD32F450VGH6 + IIM-42652 + BMM350）参照量产 335（GD32F103 真产线代码）实现
> 标定台+PC 上位机三方标定体系全链路。核心结论：**8 类标定指令入口全部打通、122 参数
> （12+12+98）sector7 Flash 存储与 335 产线逐字节一致、温补 98 浮点全链路对齐核查通过
> （零改动）、温控 PID 沿用 333 完整版**。已编译通过（AC5，0 错误，仅新增 2 条旧版头已知
> 告警），已提交（主仓 `333acb2` + 子仓 `c70fdb7`），待上板验证。

## 1. 协议指令集（与 335 完全一致，入口均为 UART/HEX 表）

帧格式沿用平台 HEX 协议（AA 55 LEN CMD ID PAYLOAD CRC），标定指令经 bsp_parse 转发至标定模块：

| cmd/id | 方向 | 功能 | 载荷要点 |
|--------|------|------|----------|
| 0x01/0x11 | PC→IMU | 温控测试 | 含目标温度等控制参数 |
| 0x01/0x12 | PC→IMU | 温漂标定启停 | CurTarget=ceil(当前温度/5)×5，5°C 阶梯 |
| 0x01/0x15 | PC→IMU | 标定六轴数据流启停 | status=1 开连续流 |
| 0x04/0x17、0x04/0x18 | PC→IMU | 位置/转台参数下载 | type=0x01 多位置[12] / 0x02 转台[12]，写 Flash 并回 ACK |
| 0x04/0x19 | PC→IMU | 温漂参数下载 | **98 浮点**，写 Flash 并回 ACK |
| 0x04/0x20 | IMU→PC | 下载应答 | type+status（下载状态机关键，延迟 1~2s） |
| 0x04/0x16 | IMU→PC | 温度实时流（采集验证备用） | 载荷 82B：temp+raw/fltr/cal 三组六轴 f32×19+保留 6B |
| 0x07/0x01 | IMU→PC | 标定六轴+温度流（主出口） | 载荷 30B：temp+accel[3]+gyro[3] f32×7+保留 2B |
| 0x08/0x01、0x08/0x02 | 标定台→IMU | 控制 / 温控 | 0x08/0x02 阶梯恒温（现行） |

## 2. 122 参数 Flash 存储（sector7）

```c
typedef struct {
    unsigned int Magic;       /* 0x5AA5C3C3 页有效标志 */
    unsigned int CalDoneFlag; /* 0xA5A5A5A5 标定完成标志 */
    float MutiPosition[12];   /* 多位置参数 */
    float Truntable[12];      /* 转台参数 */
    float TempBias[98];       /* 温漂参数 */
} BspCalibrationParam_S;      /* 8+488=496B */
```

- 地址 `IMU_501_CALIBRATION_PARAM_ADDR = 0x08060000`（sector7，128KB 独立扇区；Loader 边界
  0x08020000 之外，与产品信息页 A/B（扇区5/6）不冲突）
- 装载：`BspCalibrationInit` 仅 Magic 有效时调 `initialiseSensorInterface(位置, 转台, 温补98)`；
  无效时 memset 清零且**不调库**——依赖算法链在 `BspAlgorithmInit` 里的全零初始化调用兜底
- 保存：整扇区擦写约 1~2s **阻塞** → 下载 ACK 延迟 1~2s，上位机超时需 ≥3s；保存成功后即时重应用

## 3. 实现要点

- **单位域关键事实**：`drv_icm42688` 加速度已乘 CONSTANT_GRAVITY → 内部链 m/s²，与 335（BMI088）
  同域，标定流**无需任何单位换算层**（曾误判 g 域，读驱动后修正）
- **IIR α=0.1 沿用 335**：335 因 BMI088 噪声密度约为 ICM42688 的 5 倍而引入（满足上位机 std<1
  判定）；501 传感器更安静但沿用同款滤波对齐产线行为——200Hz 发送率截止约 3.5Hz，转台恒速旋转
  信号可完整通过
- **温控 PID**：移植自 IMU_103_333 完整版 temp_pid（Kp=1.8/Ki=0.17/Kd=0.9，1kHz 执行）；501 差异
  仅两处——起步温度取 IIM-42652 片上温度、应答与数据流走 GD32F4 平台 `UART0SendData`（335 为
  GD32F1 平台 `DrvUART0SendData`，仅平台名差异）
- **bsp_parse 转发**：8 类指令入口（0x0111/0x0112/0x0115/0x0417/0x0418/0x0419/0x0801/0x0802）
  转发封装守卫由 335 扩为 `335||501`
- **接线**（app_main）：`BspAlgorithmInit` 后 `(void)BspCalibrationInit()`，主循环 1kHz
  `BspCalibrationProcess()`；工程经 uvprojx/uvoptx 编入 `bsp_calibration.c`

## 4. 温补参数对齐 335 核查（98 vs 24 之辨，零改动）

排查结论：**501 温补参数链路与真 335 产线逐环节一致，无需改动**。库头文件注释"24 浮点"只对应
"未标定兜底全零调用"路径——真 335 产线源码（GD32F1xxMCU 仓库 bsp_algorithm.c）同样使用
`TemperatureParam[24]={0}` 全零调用；产线相关路径两侧均为 98 浮点：

| 温补参数环节 | 真 335 产线 | 501 | 一致 |
|---|---|---|---|
| Flash 布局 | MutiPosition[12]+Truntable[12]+TempBias[98]（496B） | 同构逐字节一致 | ✓ |
| 温补下载解析（0x04/0x19） | `for(i=0;i<98;i++)` | 同款 | ✓ |
| Flash 有效时装载 | `initialiseSensorInterface(pos, rot, TempBias[98])` | 同款 | ✓ |
| 保存后即时重应用 | BspCalParamSave 内调用 | 同款 | ✓ |
| Flash 无效兜底 | memset 清零+不调库 | 同款 | ✓ |
| 算法链未标定兜底 | 全零 `TemperatureParam[24]` 调用 | 同款 | ✓ |

> 教训：若擅自把兜底数组扩成 98 反而偏离 335 行为；"对齐"以产线源码为准，不以头文件过时注释为准。
> 335 产线温标设备温补生效、未标定设备姿态正常的既成事实，间接证实库对两条路径的处理宽度如上。

## 5. CAN 能力覆盖审计（2026-11-28）

结论：501 CAN 全部支持，覆盖度平台内最全（与 506 同级），比真 335 多整套 CAN（335 的 CAN 代码
为死代码，标定指令两侧均走 UART）：

| 能力 | 335 | 351 | 506 | 501 |
|---|---|---|---|---|
| 驱动+初始化（PD1/PD0） | ✗ | ✓ | ✓ | ✓ |
| 接收指令 0x100~0x118（19 项） | ✗ | ✓ | ✓ | ✓ |
| 完整/精简数据流推送 | ✗ | ✓(队列) | ✓(直发) | ✓(直发) |
| 0x119 磁/0x120 压推送 | ✗ | ✗ | ✓ | ✓(无气压计，0x120 恒 0) |
| 0x117 磁校准 CAN 进度 | ✗ | ✗(走 0x0607) | ✓ | ✓ |
| 0x111 零偏 CAN 回复 | ✗(空桩) | ✓ | ✓ | ✓ |

三条链路均核实：接收 中断→FIFO→主循环 `DrvCAN0GatewayPoll`→`BspCANParse` 查表（19 项无产品宏
守卫）；发送 `BspCanSendData`→`DrvCAN0Send`；推送 506/501 直发通道。标定改动不影响 CAN。

## 6. 上板验证清单

1. 烧录后姿态/推送正常（确认算法链全零调用兜底生效）
2. `0x01/0x15` 开标定六轴流，核对 temp+accel+gyro 数值合理性（m/s² 域）
3. 标定台多位点采集 → 0x04/0x17、0x04/0x18、0x04/0x19 参数下载（**ACK 延迟 1~2s，上位机超时
   需 ≥3s**）→ 断电重启核对参数保持（sector7 Magic 校验）
4. 温标流程：0x01/0x12 + 0x08/0x02 阶梯升温（5°C 步进），核对 0x04/0x16 温度实时流三组数据
